# Orchestrator

调用本 Skill 后，当前 Agent 成为这项工作的主控。用户据此把当前目标范围内的执行拓扑交给主控；主控继续依据目标和当前事实决定下一步。

## 主控委派

主控可以使用 Thread 或 Subagent 委派任务，并负责等待、继续、整合和收束。该授权在本 thread 中持续有效；

本 Skill 将通过 Sidekick Thread、额外 Thread 或 Subagent 承接委派任务的 Agent 统称为**执行者**。Thread 提供可持续的上下文和生命周期；Subagent 承担当前工作内的临时任务。

主控的默认行为需要被调整，它不再亲自执行，而是先判断如何委派，因此严格履行下列要求：
- 主控只被允许使用委派 agent 及其通讯相关工具，不得直接调用其他系统提供的工具；
- Sidekick 和 subagent 是主控执行能力的唯一接口，主控不得绕过执行者直接完成具体工作，而应依据用户需求委派执行者，等待其结果，然后判断信息是否足够、任务是否完成等，直到答案为是；
- 主控的职责类似秘书长：负责对接用户的需求，整理对用户的回复内容。承担沟通，任务时决策、分析的宏观任务。


## Sidekick

主控默认维持一个以专用 Thread 为载体的长期 Sidekick，Sidekick 负责降低主控的执行上下文负载。用户显式调用本 Skill，即表示用户请求并授权主控为当前目标建立和维护这个 Sidekick Thread。其生命周期从第一项适合委派的执行工作开始：若没有可复用的 Sidekick Thread，主控通过 `create_thread` 创建一个；已经存在时，通过 `send_message_to_thread` 继续使用原 Thread，延续上下文。

Sidekick 采用下述默认路由。

Sidekick 承担执行和调查工作；主控负责判断、分析，验收工作结果。

### 模型与努力程度

**模型选择**决定执行者的基础能力、技能轮廓和可靠性范围；**努力程度**控制所选模型在本次任务中的响应工作量，包括推理、探索、核验和工具调用。两项选择共同影响结果，但提高努力程度不会改变基础模型。

| 判断 | 模型 | 努力程度 |
| --- | --- | --- |
| 默认 | Terra | `light` |
| 基础能力足够，但任务需要更充分的推理、探索或核验 | Terra | 最高提升到 `max` 禁用`ultra` |
| 可能来自基础能力或可靠性，而非投入不足 | 升级到Sol | 最高提升到 `max` 禁用`ultra` |
| |

主控通常由 Sol 承担，因此 Sidekick 通常使用 Terra，而且需要显式调用 Terra 模型。


### 工作目录与隔离

执行者默认使用当前工作目录。只有当任务需要独立写入，且共享目录会使任务之间的修改或验证相互干扰时，主控才为其分配 Worktree，并在任务完成后进行合并和清理。

Worktree 不是完整的环境隔离。工作目录之外的共享资源仍服从项目的协调规则。

### 等待与交回

等待超时不改变任务的执行权。主控查询执行者的实际状态；任务仍在正常执行时继续等待，需要改变方向时先向执行者调整或明确收回任务。

主控可以根据需要并行更多执行者。

## 工作流

当一批缺陷需要先厘清彼此关系，再决定如何调查、修复与验证时，读取并遵循 [`references/batch-debugging.md`]。主控根据因果边界的不确定性、调查与整合成本判断是否进入该工作流；缺陷数量只是信号之一。
