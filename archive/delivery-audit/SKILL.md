# 交付审计

把事实与行为主张交给可复核依据，把交付是否值得接受交给选择审计。

## 1. 确定交付边界

明确本次审计针对当前任务、Agent 交接、分支或工作树，还是多 Agent 整合结果。重建用户目标，并检查实际产物、验证证据、已有工作 Agent 汇报和已有代码审查结果。仅消费已有的 `codex review` 结果，由当前工作流决定是否另行运行代码审查。

多 Agent 场景中，工作 Agent 对自己的交付负责；整合 Agent 还要审计合并与兼容产生的新选择。缺少某个工作 Agent 的依据时，检查其产物或联系它；仍无法取得时标记为未验证。

**完成条件：** 目标、产物、证据范围和交付责任已明确。

## 2. 披露选择与评估支持

列出用户未预先指定、但会实质改变问题定义、范围、架构、通用性、外部行为、风险、验证标准或延期工作的全部选择。对每项说明决定、后果、依据、剩余不确定性和 Agent 立场，省略不影响结果的机械细节。

引用只负责定位来源；证据是来源或观察中实际支持某项主张的内容。文档可以证明适用范围内的合同或事实，源码可以证明实现状态，测试、日志和可见结果只能证明对应 revision 与条件下观察到的行为。检查来源权威性、与主张的直接相关性、当前场景适用性、证据完整性和反证；不得把“附有引用”直接升级为“正确”。

为每项依据标记认识状态：

- **已确认：** 在声明范围内有直接、适用且可复核的权威依据或观察结果，没有未解决的反证。
- **有支持：** 有相关依据，但仍存在覆盖范围、间接性或独立性缺口。
- **推论：** 由已确认内容推导，推导链已披露，但尚未被直接观察。
- **假设：** 为继续工作暂时采用，尚无充分支持；说明如何验证以及错误时的影响。
- **未知：** 当前信息不足，不能形成判断。
- **已反驳：** 有直接且适用的依据与主张冲突。

无法由事实决定的设计取舍标记为**启发式判断**，不得伪装成已确认事实。只有虚构来源、运行结果或观察，或者把已知不存在的内容表述为事实，才标记为**虚构**并阻止接受。

Agent 对决定的立场只能是**建议采用**、**保留意见后接受**、**暂缓决定**或**不建议采用**。立场表达风险判断，不改变依据的认识状态。

**完成条件：** 每项实质性自主选择都有后果、依据、认识状态、剩余不确定性和明确立场；权宜处理、特例修复、未验证假设与超出证据的成功声明均已披露。

## 3. 按风险决定独立审计

当失败后果显著、存在重要自主设计、证据弱于结论，或交付整合了相互作用的组件或工作树时，派出全新上下文的只读 SubAgent；确实难以判断时也执行。工具或上游指令不允许委派时，将独立审计标记为未完成的证据边界并说明影响。其余情况跳过，并简述理由。

只向审计 Agent 提供用户目标、原始产物或 diff、相关项目指令和已有依据，让它独立重建选择与认识状态。收到审计结果后，当前 Agent 将其与执行 Agent 的披露比较。只保留有具体依据的遗漏选择、错误通用化、目标漂移、引用不支持主张、证据不适用或不完整、遗漏反证，以及后果显著不同的替代方案；没有异议也是有效结论。

**完成条件：** 独立审计已完成、合理跳过或明确标记为未完成；所有异议都已由证据解决或保留为待裁决事项。

## 4. 汇报门禁

先给出**接受**、**满足条件后接受**或**暂不接受**，再报告实质性选择及其认识状态与 Agent 立场、独立审计结论、证据缺口和待用户裁决事项。只把产品、架构或风险取舍交给用户；明确说明无需用户判断的情况。

交付因审计发生变化后，对修改结果重新运行本门禁。

**完成条件：** 所有接受条件、异议和证据边界均已披露，并明确标记为已解决、保留或升级给用户。
