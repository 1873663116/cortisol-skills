# ADR 架构决策记录格式规范

架构决策记录（ADR）统一存放于 `docs/adr/` 目录下，并使用递增序列编号命名：`0001-slug.md`、`0002-slug.md` 等。

采用按需懒加载创建 `docs/adr/` 目录——仅在需要记录首个 ADR 时才创建该目录。

## 核心模板

```md
# {决策的简明标题}

{1 到 3 句话：背景上下文是什么、我们做出了何种决定、以及为何做出该决定。}
```

仅此而已。一篇 ADR 完全可以只有一个精悍的段落。其核心价值在于记录“我们做出了某项决策”以及“背后的核心动因”——而不是为了流程机械地填满模板各个章节。

## 可选章节

仅在能够提供实质性价值时方可增加以下章节，绝大多数 ADR 并不需要它们：

- **状态（Status）** Frontmatter 元数据（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——在决策被重新审视或废弃更替时极具价值。
- **被否决的备选方案（Considered Options）**——仅在被放弃的替代方案确实具有长期参考和防坑价值时补充。
- **长远后果（Consequences）**——仅在存在非显而易见的下游衍生影响需要显式警示时补充。

## 文件编号

扫描 `docs/adr/` 中现存的最大编号并加 1 递增。

## 何时方可提议编写 ADR

必须**同时满足**以下全部三项条件：

1. **不可逆性高（Hard to reverse）**：后续推翻决策并重新调整的成本极其高昂。
2. **缺乏背景时令人费解（Surprising without context）**：未来的读者阅读代码时会由衷困惑“他们当初为何要以这种非显而易见的方式设计？”
3. **真实权衡取舍的产物（The result of a real trade-off）**：存在过实质性的备选方案，且出于特定动因最终选择了当前方案。

若一项改动极易回退调整，则无需记录——直接在后续需要时修改即可；若方案本身顺理成章、显而易见，没人会对此产生疑问；若根本没有其他合理的备选方案，除了一句“我们做了理所当然的选择”外没有任何额外信息可沉淀。

### 属于 ADR 范畴的典型决策

- **核心架构形态**：“我们采用 Monorepo 单体多包仓库。”“写模型采用事件溯源（Event-Sourcing），读模型异步投影到 Postgres。”
- **上下文间的跨域集成模式**：“订单域与结算域通过领域事件异步通信，严禁使用同步阻塞式 HTTP 调用。”
- **具有长期锁定效应的重大技术选型**：底层数据库、分布式消息队列、身份认证平台、部署目标基础设施。并非所有第三方库都需要记录——仅限那些一旦需要替换将耗费数月工程周期的重度依赖。
- **系统边界与所有权归属划分**：“客户数据全生命周期由 Customer 上下文独占持有；其他上下文仅允许通过 CustomerId 弱引用。”明确的否定规则与肯定规则同样具有巨大价值。
- **对显而易见路径的刻意偏离**：“出于 X 维度的极致性能要求，我们采用手写原生 SQL 代替 ORM 框架。”任何理性读者初看可能会做出相反假设的地方均须记录，这能有效防止下一位工程师以“重构”名义误删深思熟虑的设计。
- **代码本身无法体现的外部强约束**：“出于行业合规审计要求，我们无法使用公有云对象存储。”“由于上游合作伙伴的接口契约限制，接口响应耗时必须严格控制在 200ms 以内。”
- **被放弃方案的否决动因非显而易见**：若当初在深入调研后放弃了 GraphQL 而选择 REST，记录其深层考量，否则六个月后很可能会有另一位同学再次提议引入 GraphQL。
