### 功能开发（Feature）

**对功能架构设计负全责。严密规划、代码审查、严格验证。** 编码实现可委派给子 Agent，技术主导权始终掌握在自己手中。

1. 对受影响的子系统调用 `how` 技能梳理实现脉络。
2. 调用 `architect` 技能并行探索多种架构设计方案。若选择跳过，必须记录 `architect skipped: <跳过原因>`，严禁悄悄将设计决策与具体实现混在一起。
3. 将吞吐检查点（Throughput Checkpoint）明确拆解为四项待办。当某一维度确实不适用时（如单文件改动、无扇出场景），该条目仍须保留并标注 `n/a: <不适用原因>`，严禁直接删除：
   - **阻塞性前置步骤。** 所有质量门禁必须在任务扇出前执行完毕。
   - **正交独立工作流。** 涉及的文件、服务或架构层次互不相交时坚决并行；存在共享写入依赖时串行。
   - **共享可变状态。** 默认拆分隔离消除共享（遵循**在串行化共享状态前先消除共享**原则）。仅在存在真实强不变量约束时才串行。
   - **最小安全拆分粒度。** 若单个 Worker 最为合适，明确陈述技术理由。
4. 阅读 **dispatch** 技能规范选定 `Letter-precise`（字面精准）角色，经 **orchestration** 技能派发具体编码任务，并给出清晰限定的作用域，包括目标文件路径、明确命名的数据结构与形态及其组织结构，以及明确的成功验收标准。数据形态的组织结构按照 `../../principle-model-the-domain/SKILL.md` 确定：用状态机替代散落的布尔标记、用映射表/注册表替代条件分支、用强类型模型替代重复的结构假设，且必须在被委派方着手编写业务逻辑前完全敲定。生成的 diff 必须由你亲自严格审查。当实现路径存在多种合理的技术方案时（如错误处理机制、抽象层设计、测试架构），改用 **arena** 技能进行委派比选，让多个 Runner 产出相互竞争的候选方案，并通过跨模型交叉评审把关最终选型。本步骤为硬性要求，不存在“附带理由即可跳过”的例外，极简工程原则（Laziness Protocol）亦不得推翻此项规范（此处换取的是代码审查的独立客观性，而非单纯节省代码行数）。即使你自身正处于被委派的 Worker 上下文中，亦可继续经 **orchestration** 技能再行委派；“本项目规模极小”或“Worker 无法再派生任务”等借口均不成立。在受限无法再委派的特殊环境下，满足本步骤要求的方式为由自身直接对 diff 负全责并保持同等严格的审查标准，严禁输出“待命中”并干等嵌套委派。代码注释严格遵循 **Comments** 章节规范。采用外科手术式的精准局部编辑；衍生自上游的文件必须回到源头重新校对。共享底层原语的增强必须同步移植至所有使用方，并逐一进行严格验证。鼓励小步快跑、多提细粒度 commit。
5. 在匹配的宿主界面上执行闭环验证。“结论不确定”或在错误界面上测试均不得视为通过，必须明确指出来。
6. 执行 rebase 整理为一系列小巧有序的 commit 链；后续工作基于此进行堆叠。遵循**将工作划分为闭环可验证单元**原则，每个细粒度单元均完成构建、验证、提交后，再启动下一个。
7. 若架构设计存在争议，合并上线前调用 `interrogate` 进行对抗式审查。
8. 执行**开 PR（Opening a PR）**。

代码层面紧密耦合的任务（单一完整功能、整块迁移）应交由单个 Owner 负责，并将吞吐检查点内联注入其上下文；该 Owner 在阻塞阶段完成后自行向内扇出。父级上下文的扇出仅保留给能产出独立交付物的正交切片（如安全审计、跨子系统调查、对比实验）。触及开发阶段边界时必须重新规划检查点；派生全新的 Owner 承接下一阶段，严禁将上下文无限串联。

**最终回复要求：** 已构建的功能概述、方案选型结论及决策理由、尚待决定的遗留事项。方案比选详情以 Markdown 表格形式呈现。
