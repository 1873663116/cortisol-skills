### 性能轨迹取证（Trace forensics）

**对基于性能分析产物输出准确诊断负全责。加载文件、结构化转换、聚焦收敛至病因、精准归因至源码。** 适用于收到用户提供的 `.cpuprofile`、`Trace-*.json.gz`、`Spindump.txt` 或 `.heapsnapshot` 文件，并伴随“这里为什么变慢、无响应、发生泄漏或崩溃”的求助场景。

本流程与**运行时取证**严格有别：后者侧重于对活跃运行的进程进行动态实时插桩；而本流程中性能采集已经完成，交付物为静态的离线数据集，只需深入分析现有文件，严禁重新运行该程序。分析工具应保持通用以便于跨平台移植：使用 Chrome DevTools 或 Trace 解析器分析 cpuprofile 与 `.json.gz`，使用文本编辑器查阅 spindump，使用堆分析工具处理 heapsnapshot。

1. **识别格式并选取适宜工具加载。** 超大体积的数据文件交由子 Agent 解析（遵循 `../../principle-guard-the-context-window/SKILL.md`），主线程仅保留提炼后的核心发现。
2. **将原始产物转换为可结构化查询的形态。** 将 Trace 采样点或堆内存快照导入本地 SQLite 数据库，每行对应一个采样点（sample）、调用帧（frame）或内存节点（node）。先完成可查询形态的转换，再展开深度分析。
3. **聚焦收敛根本原因。** 查询耗时占比最高的调用帧，顺着调用树精准定位核心热点路径（hot path）。排查内存泄漏时，顺着对象保留链（retainer chain）从泄漏对象向上回溯至 GC Root。分析 spindump 时，找出持续占用 CPU 或处于死锁阻塞状态的异常线程及其具体的等待原因（wait reason）。
4. **精准映射归因至源代码。** 利用分析产物自带的符号表，将热点帧精准映射至具体的文件路径、符号名称及具体代码行。若调用帧缺少源码映射，则诊断尚未闭环；必须完成符号解析，或明确注明该产物未携带符号表。
5. **依托成对的基线采集进行交叉比对验证。** 若手头具备改动前后的成对性能分析文件，深入比对两者差异，确保所定位的归因点确实对应真实发生的性能衰退，而非背景环境噪声。若缺少对照样本，则必须将结论明确标注为“该分析产物所能支撑的最强假设”，而非已百分之百确诊的根本原因。
6. **交付附带详实证据的诊断报告。** 除非用户显式要求，否则不提供代码修复；根本原因查明后，根据具体问题类型路由至缺陷修复（Bug fix）或性能问题（Perf issue）流程。吞吐检查点单行记录为 `throughput checkpoint: n/a, read-only forensics`。

**最终回复要求：** 性能分析产物名称及格式、提炼收敛后的核心诊断结论、源码精确对应位置、分析产物文件存储路径，以及是否存在成对采集样本完成交叉验证。
