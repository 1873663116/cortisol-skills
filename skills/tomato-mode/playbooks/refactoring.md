### 重构（Refactoring）

**你对外部行为契约负全责。调整代码结构，坚决保持既有外部行为严格不变。** 适用于“重构代码”“重命名符号”“函数抽取”“内联化”“代码去重”“模块重新组织”“迁移该模块”“整理这块逻辑”。本流程与新增业务行为的“功能开发”严格有别，亦与纠正错误行为的“缺陷修复”严格正交。

重构一旦夹带行为变更，就会彻底丧失其安全性基石。若在清理过程中发现缺失的功能逻辑或真实的隐藏 Bug，必须将其单独拆解出去，首先严格按照既定行为契约完成纯粹的结构性重构并发布。允许在重构中引入全新架构设计，但必须明确指出并按规范路由至功能开发流程。大规模或跨子系统的系统性结构改造（如跨大量调用点的全面迁移、多子系统协同调整）属于 **figure-it-out** 技能管辖；本 playbook 专注于聚焦的中等规模重构任务。

1. **确立并锁定行为契约锚点。** 针对受影响的子系统调用 **how** 技能透彻厘清当前对外契约。在触碰任何实际代码结构前，必须先编写能够精准刻画现有行为的表征测试（Characterization test）、快照用例或等价性验证测试台（Test harness）。唯有在此类坚固测试台的护航下，“重构”才是一项具备可检验性的真实承诺（遵循 `../../principle-prove-it-works/SKILL.md`）。若当前区域缺乏测试覆盖，必须先补齐表征测试锚点，再改动结构；静态类型检查与 linter 校验绝不能等同于行为测试锚点。
2. **基于领域模型确定目标结构。** 遵循 `../../principle-model-the-domain/SKILL.md` 识别代码中缺失的领域结构：用状态机替代散落各处的布尔标记、用映射表/注册表替代四处铺开的条件分支、用强类型模型替代重复的数据结构假设、用纯粹的 reducer 替代随意散落的可变状态操作。对于形态本身清晰且局部内聚的代码，保持平铺直叙的实现即可；重构调整结构必须以消除分支复杂度或排除非法状态为目标，严禁凭空增加无意义的间接层。
3. **明确目标架构形态。** 思考若从零构建，理想的模块划分、类型定义与调用拓扑应是何种形态（遵循 `../../principle-foundational-thinking/SKILL.md` 与 `../../principle-redesign-from-first-principles/SKILL.md`）。若目标结构跨越了函数或模块边界，在动手搬动前必须先调用 **architect** 技能进行多方案并行设计探索。
4. **先做减法再做加法。** 在引入新的结构形式前，先彻底清理废弃死代码、消除仅有一个调用方的单层包装函数、精简冗余校验逻辑、清理无用引用（遵循 `../../principle-subtract-before-you-add/SKILL.md`）。最终交付的代码应当是达成目标形态的最小必要改动（遵循 `../../principle-laziness-protocol/SKILL.md`）。出于“可能有用”心理添加的投机性清理必须坚决回滚，严禁顺水推舟混入。
5. **小步快跑推进，确保测试锚点全程保持绿态。** 接口签名或 API 的重构调整必须在同一批次中同步迁移所有外部调用方并彻底物理删除旧 API（遵循 `../../principle-migrate-callers-then-delete-legacy-apis/SKILL.md`）。严禁保留临时兼容垫片（shim），严禁新旧双轨路径并存。每次重命名操作都必须在真实代码文件中进行全局交叉检查，防止遗漏字符串引用、文档注释以及反射式动态调用。阅读 **dispatch** 技能规范选定 `Letter-precise` 角色，经 **orchestration** 技能将机械性的代码编辑任务派发给 Worker，并明确指定作用域（文件路径、待调整符号名称、必须保持不变的行为契约）；生成的 diff 必须由你亲自严格审查。
6. **在真实产物上端到端验证行为未发生变化。** 严禁用“编译通过了”充当验证依据（遵循 `../../principle-prove-it-works/SKILL.md`）。较大幅度的结构重构必须执行严格的等价性校验：编写脚本比对新旧输出差异、基于录制的流量基线进行回放验证，或通过对应的控制类技能在匹配的宿主界面上执行端到端冒烟测试。验证责任由你本人全权承担，严禁轻信被委派方“看起来没问题”等主观结论。
7. **验证改动切实降低了系统复杂度。** 衡量重构是否成功的硬性指标是读者心智负担的显著下降（遵循 `../../principle-minimize-reader-load/SKILL.md`）：从提出疑问到找到答案之间的调用层级更少、隐式状态更少、无第二处调用者的无意义间接层更少。若本次重构生成的 diff 未在任何维度上切实降低阅读与维护负担，坚决回滚本次改动。
8. **整理为逻辑清晰的提交序列。** 通过 rebase 整理为一系列小巧有序、自解释的 commit 链：先提交纯做减法的清理 commit，再提交核心结构改造 commit，最后提交收尾清理 commit，确保在未来发生意外时可精准单独回滚特定切片。遵循**将工作划分为闭环可验证单元**原则，确保每个 commit 均保持测试绿态通过后再开启下一步。最后执行**开 PR（Opening a PR）**。

**最终回复要求：** 代码结构的具体调整内容、用于锁定行为的测试锚点定义、等价性证明数据或结果、读者心智负担的具体改善指标、已正式交付的改动清单与已被主动回滚的改动清单。严格保证无任何未声明的行为变更。
