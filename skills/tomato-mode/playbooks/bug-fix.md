### 缺陷修复（Bug fix）

**你对该修复任务负全责。做好规划、代码审查与严格验证。** 将具体调查与修复实现委派给子 Agent，自身始终保持技术主导。

保持严谨的科学态度。上线的每一行代码都必须能追溯至确凿的运行时证据。出于“万一有用”心理添加的防御性冗余代码只是未经验证的假设，绝不能当作修复方案，严禁上线。当实测证据推翻某项假设时，必须坚决回滚因该假设而引入的所有改动。仅交付证据所能支撑的最小必要改动，多一分都不行。该纪律同样适用于性能问题（Perf），只是那里的核心证据是性能分析轨迹（trace）。

1. **在相同宿主界面上亲自复现。** 通过对应的控制类技能在匹配的运行界面上亲自稳定复现问题（参见 Non-negotiables 章节）。严禁将复现步骤推给用户。即便某项调试或插桩规范建议询问用户，也不得覆盖本条原则，你必须亲自驱动插桩后的运行时环境。仅当给出明确、具体的客观理由证明控制界面确实无法触达目标时，且在你已将其驱动至极限后，才允许向用户求助。若无法直接复现，应主动逼出问题：构造合成触发条件、收紧边界环境，或持续添加运行时插桩直至问题触发。无法稳定复现的 Bug，永远无法证明其已被真正修复。
2. **二分排查根本原因。** 提出候选假设，通过实测证据逐一排除，直到唯一下结论得以留存。调用 `how` 技能梳理受影响子系统的实现逻辑，调用 **why** 技能追溯历史回归记录，以此构建初始假设集合。在每一轮排查中，选择能够切分排除最大剩余问题空间的路径，获取运行时证据并完成证伪排除。当程序运行时状态模糊不清时，添加插桩或日志输出，在代码执行过程中实时观察，严禁凭空猜想。面对漫长或顽固的问题追查，使用 Cursor 的 `/loop` 命令持续推进。在进入步骤 3 的 architect/interrogate 扇出之前，必须先用运行时证据严格确认幸存下来的*底层机制*；基于看似合理却未获证实的虚假原因所做的架构设计，即便全员达成一致也可能全盘皆错，而真正的病因往往潜伏在相邻的子系统中。
3. **规划修复方案。** 若改动跨越函数或模块边界，必须先调用 `architect` 技能。阅读 **dispatch** 技能规范选定 `Letter-precise`（字面精准）角色，经 **orchestration** 技能派发具体实现任务并限定明确的作用域；严格审查生成的 diff。
4. **在相同界面上执行闭环验证。** 最初的复现用例现在必须稳定通过。“结论不确定”或在错误的界面环境下测试均不得视为通过，必须如实标注。单元测试仅能证明特定分支逻辑的执行情况，无法证明 Bug 已彻底消除。
5. **规范组织 commit 提交顺序。** 确保失败的复现用例在 Git 提交历史中排在修复代码之前，让 diff 本身呈现清晰的证明逻辑。当 Bug 拥有低成本的本地测试路径时，遵循 **tdd-bug-fix** 技能（`../../tdd-bug-fix/SKILL.md`）先写红态失败测试的节奏推进；当测试成本极高、重度依赖外部集成环境或测试方案不明朗时可跳过。
   这正是**将工作划分为闭环可验证单元**原则技能的典范形态：先提交红态测试，修复代码叠在其上。
6. **执行开 PR（Opening a PR）。**

调查阶段可将 `how` 与 `why` 作为并行的子 Agent 扇出执行。

**最终回复要求：** 故障现象描述、根本原因分析、具体修复方案、验证执行方式。原样附上从失败（红态）到成功（绿态）的完整复现输出日志。
