### 自主运行

**对任务退出条件负全责。先明确定义何为“完成”，随后一气呵成推进至终态。** 适用于“我去睡了”“持续运行直到完成”“/loop 直到 X”等场景。

1. 在首轮迭代前，将退出条件明确定义为一个可程序化检查的布尔判定式（例如：测试全部通过、复现用例被成功修复、全部 N 个 PR 均已合并、像素 diff 归零）。模糊的目标会导致流程停滞，明确的判定式才能给出清晰的终止信号。
2. 使用 Cursor 的 `/loop` 命令（内置命令，非 pstack 技能）选取唤醒机制。对于存在明确监听事件的场景（如 CI 运行、PR 合并、Git ref 更新），配置一个 Watcher 子 Agent 并在事件就绪时唤醒主流程，同时辅以长周期的基于时间的心跳兜底；对于无特定事件的场景，采用固定间隔心跳，周期长短依据“产物经过多久值得重新检查一次”来设定。
3. 每次迭代仅做出有充分证据支撑的最小改动，并对照判定式进行验证。取得进展则立即提交 commit，无实际效果的改动坚决丢弃。那些出于“万一有用”心理添加的防御性冗余改动必须立即回滚，严禁顺带混入。遵循**将工作划分为闭环可验证单元**原则技能编排任务序列，步步为营、逐一验证，严禁将检查集中堆积到最后。
4. 执行过程中发现的衍生问题由你自主全权处理。包括损坏的技能、关联 Bug、不稳定（Flaky）的校验脚本、代码评审噪音、工具报错、未决的后续项以及可修复的逻辑漂移，均通过 tomato-mode 自主排查解决。计划外的修复应单独开 PR 提交。严禁将可逆工作搁置等待人类，更不要随意调用 `AskUserQuestion`。仅在遇到不可逆破坏性写操作、任何实验均无法定夺的纯产品定义/偏好抉择，或已陷入确凿的技术死胡同时，才向人类升级求助。始终将退出判定式作为核心推进主线，每解决一个附带问题后立即回归主线。
5. 每次迭代均须通过 **show-me-your-work** 技能记录一个检查点，单行明确说明改动内容及判定式是否向前推进。缺少决策记录链的执行既无法被审计，也无法在中断后准确续接。
6. 一旦判定式得到满足立即终止循环。遇到指标停滞的瓶颈期绝非停工的理由，应及时调整策略、尝试新思路来打破瓶颈。遇到确凿死胡同应及时向人类汇报而非盲目死循环，严禁通过放宽判定式来虚假宣布胜利。

**最终回复要求：** 退出条件定义、已执行迭代次数、正式合入的改动、已丢弃的改动、判定式的最终评估状态。
