### 全自动驾驶

**你负责把控全局裁决，而非包揽各个具体 PR。每个 PR 由专属 Owner 全程负责从构建直至合并，未经 Swarm 审查并给出干净（Clean）裁决前，严禁合并任何 PR。** 适用于“全自动驾驶这一队列”“完全自动驾驶”以及“单 PR 单 Owner 推进”的项目。核心任务是将一列相互独立的 PR 完全自主推进至全部合入主线。每个 PR 的 Owner 承接该 PR 的整个生命周期；根节点调度器仅保留验证把关、会签审批与全局审计职责。

1. **标出操作人员专属条目并严格遵守“先陈述后等待”。** 操作人员显式指定的条目由其本人全权掌控。由其亲自把关评审并执行合并点击操作，任何自动化 Owner 均不得代为合并。当操作人员要求陈述协议规范或执行计划时，清晰输出陈述内容并立即停下等待。仅在其给出明确放行指令后方可开始执行。
2. **每个 PR 指派专属 Owner 负责完整生命周期。** 每个 PR 分配一个专属的 Cursor 云端 Agent（Owner），负责代码构建、Graphite（gt）分支注册、在真实产物上端到端自证（遵循**用实际运行证明有效**原则）、按照 `../references/bugbot-triage.md` 审慎分流 Bugbot 意见、执行一轮 **unslop** 去 AI 腔清洗、运行 `/no-comments`（**no-comments** 技能）、向当前主干（trunk）执行 restack、运行 Babysit 看护循环直到 CI 全绿（`playbooks/babysit.md`），以及最终的合并操作。向主干 restack 必须始终排在 Babysit 流程之前，绝不等到发生代码漂移或冲突才被动处理。每个 Owner 均须按照 **show-me-your-work** 技能在本地记录一份 decisions.tsv 决策日志，无需提交入库，在汇报时随报告一同附带。合并操作是 Owner 唯一不得擅自执行的步骤，必须由步骤 4 的安全闸门把关。
3. **保持 Owner 之间完全并行，严禁相互堆叠。** PR 彼此独立时可同时并行运行多个 Owner：单分支单写入者，文件修改严格正交，跨 PR 的主干漂移由 rebase 自动吸收。仅在改动范围存在实质重叠时才串行执行。独立 PR 直接从 main 主分支拉出，具有前后依赖的工作遵循“先合入再拉新分支”的原则。所有 PR 仍须注册至 gt（Graphite 元数据规则用于 UI 协同，而非强制依赖 stack）。唯一例外：当某个 Owner 必须拆分具有直接依赖的改动时，可维护一条局部的短私有 stack。
4. **在合并前对每个就绪 head 进行 Swarm 深度验证。** 当 Owner 报告某个 head SHA 已就绪可合并时，调用 **swarm** 技能并行扇出多个独立的验证通道，汇总生成一份最终裁决。具体的扇出调度机制见 Swarm 技能，无需在此复述。各验证通道在目标 SHA 上重跑全部质量门禁，在真实运行环境下对核心承重行为进行现场验证，并在完全不信任 PR 描述文本的前提下深度审计凭据与 diff。浏览器、Electron 及 Web UI 场景调用 **playwright** 技能。本地无驱动 CLI/TUI 的专用技能，需直接手动操作。现场真实环境验证属于最低底线，缺少该环节的裁决无效。未经根节点签署干净（Clean）裁决，严禁执行合并。发现的缺陷退回 Owner 实施向前修复（fix-forward），修复后的新 head 必须重新启动一轮 Swarm 并生成新的裁决。
5. **获得干净裁决后由 Owner 执行合并并认领下一任务。** Owner 仅允许从最新 restack 到主干的 head 执行合并。就绪报告必须基于与主干完全同步的 head 做出，Swarm 裁决同时锁定该 SHA。若主干在合并前再次更新，重新验证规则遵循 `playbooks/shipping.md` 中的 patch-id 策略：除非 patch-id 保持一致，否则新的 head 将导致既有裁决失效。Owner 使用 Squash 方式合并自身 PR，并立即从队列中领取下一个相互独立的待办项。操作人员的全局自主授权加上根节点的干净裁决，构成了完整的合并放行授权（这是 Babysit 流程自身所不具备的）。操作人员指定的条目则停在就绪状态，等待其人工点击合并。
6. **运行根节点调度与审计层。** 真正意义上调高被锁定的门禁或预算阈值（例如 CI 仅允许收紧的门限）需要根节点重新签署，且仅在验证通道拿出确凿证据后方可批准。合并主干上已有的最新数值属于吸收漂移，而非主动调高。依托云端休眠唤醒链（一个能够自我重新武装唤醒的休眠云端 Agent），大约每 30 分钟对所有 Owner 执行一次全局审计。每次审计通过云端 Agent 的状态与存活性探针检查其运行状况，审查任务进度与协议执行严密性，并收集各 Owner 的决策轨迹。当发生批量合并时，执行一轮复盘回顾，并对合并后的机器人评论进行集中清扫。
7. **一旦操作人员发出暂停指令立即停手。** 操作人员的暂停或终止指令必须立即以“零写入（zero-writes）”形式下发至所有 Owner。各 Owner 立即冻结当前任务状态，直到操作人员明确解除限制。

**最终回复要求：** 任务队列详情（各 PR 的 Owner、当前状态及 head SHA）；各项裁决及生成该裁决的 Swarm 详情；已合并的内容及各 Owner 紧接着认领的任务；已批准的会签项及其理由；仍挂起等待操作人员把关的闸门；汇总的决策记录链存放位置。
