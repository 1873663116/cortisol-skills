### 上线（Shipping）

**对正式合入主线的内容负全责。独立验证每一个 PR，仅合入自根节点分支起连续通过验证的分支段，合入期间严禁触碰队列结构。** 适用于“合入整条 stack”“正式上线发布”“开启 merge when ready”，或承接 **Babysit** 推进至 CI 全绿后的后半程交付流程。

本流程是 `playbooks/babysit.md` 的后半程承接阶段。Babysit 负责将整条 stack 推进至具备合并条件；上线流程则负责裁决其中哪些 PR 真正达到安全合入标准，并交由 Graphite 自动排干合并队列。CI 全绿绝不等于真正安全，本 Playbook 正是用来消除二者之间的质量落差。

1. **开启任何自动合并前，必须独立验证每一个 PR。** 为每个 PR 分配一个独立的子 Agent 进行验证（严禁打包合并验证）；每个子 Agent 在真实界面环境下深度比对 parent 分支与当前 head 分支的实际运行差异。浏览器、Electron 与 Web UI 场景调用 **playwright** 技能。本地无驱动 CLI/TUI 的专用技能，验证者需直接手动操作。每个验证者必须返回明确的 `PASS`、`PASS+NOTES` 或 `FAIL` 裁决，并将裁决记录直接评论在对应的 PR 讨论串中，使审计凭据在会话之外持久沉淀。安全性的核心在于获取未经手该代码编写的独立 Agent 所给出的客观裁决；CI 全绿不是裁决，机器人给出的自动批准同样不是有效裁决。
2. **仅合入自底部根节点起连续通过验证的分支区间。** 从最低的未合并 PR 向上遍历，在第一个未通过验证的 PR 处立即截断停步（其中 `PASS` 与 `PASS+NOTES` 均视为通过）。位于未验证 PR 之上的后续已验证 PR 严禁合入主线，因为强行合入会将底层的质量断层一并带入主干。在汇报中将截断上限明确标示为具体的 PR 编号，并详细说明阻断验证链条的具体原因。
3. **重新核验各项裁决是否依然对当前代码有效。** 任何 restack 操作都会重写其上方所有分支的 commit SHA，在不触发任何 CI 告警的情况下悄无声息地使所有既有裁决全部失效。在采信较早的裁决前，必须使用 `git patch-id` 比对裁决时的 SHA 与当前 head 分支；若代码发生实质漂移必须重新验证。历史上曾出现过一轮中有 21 个裁决因 restack 而全部静默过期的严重事故。
4. **通过 Graphite 开启 merge-when-ready 并显式传入 `--always`。** 空操作的 submit 会跳过 Graphite 的状态同步，导致未能实际开启自动合并，表面上却极具迷惑性地显示为成功：
   ```bash
   gt submit --merge-when-ready --always --update-only --no-interactive
   ```
5. **严禁在堆叠分支上开启 GitHub 原生 auto-merge。** 在 stack 结构中，仅有根节点 PR 指向受保护的主干分支（trunk）。每个子 PR 均指向其未受保护的父分支且状态通常显示为 `CLEAN`；一旦开启 GitHub 原生 auto-merge，GitHub 会立刻将子 PR 提前合入其父分支，导致整条 stack 结构向内坍塌。确保合并严格按顺序执行的核心依赖于 Graphite 的协调机制。若前序 Agent 误开启了原生 auto-merge，使用 `gh pr merge <n> --disable-auto` 予以禁用，并核实该字段已恢复为关闭状态。
6. **严禁将 `autoMergeRequest` 字段作为 MWR 已开启的有效依据。** 在 Graphite 轮转到队列最前方的当前 PR 之前，该字段始终处于关闭状态；直接读取未开启状态毫无意义，据此误判会导致针对本就正常的分支执行多余的重新提交。必须通过 Graphite 自身的状态命令确认 MWR 是否生效。若无法直接确认，如实陈述事实，严禁主观推断。
7. **合并队列一旦开始排干推进，严禁触碰整条 stack。** 严禁执行 `gt sync`，严禁 restack，严禁投机性 push，严禁执行 `gt submit --stack`（后者会向下游篡改正在合并中的 PR）。即便执行普通 `gt submit`，在本地 Graphite 追踪元数据发生偏离时也可能误改 base 分支；因此严禁在未刚刚重新校对过父子关系的 Worktree 中运行 `gt`。正交独立的新任务必须重新挂载至主干分支（trunk）单独上线。
8. **静观队列自动排干，切忌手动干预打乱时序。** 在连续验证通过的区间上以 queued 模式启动 Watcher，在 `/loop` 的 dynamic 动态模式下保持监控，在每次采取行动后重新武装，直至在截断上限处达到 `COMPLETE` 状态。`ADVANCE` 代表队列向前推进，而非终止信号。每个 PR 合并完成后其下游 base 分支会被重定向，`graphite-base/*` 的临时 ref 会被自动清理，这属于 Graphite 的正常运作表现，并非故障损坏。逐一汇报每次合并事件与新的截断上限。若队列卡住，必须先诊断原因再做改动，因为处于卡死状态的队列与损坏的 stack 从外部表象看完全一致。
9. **触达验证截断上限立即停止。** 验证通过的连续区间全部合并完成后，汇报已成功合入的内容、下一个未通过验证的 PR 是哪一个，以及打通该验证所需的具体条件。扩展合并区间意味着必须严格重走一遍步骤 1 的全量验证流程，严禁擅自拍板越权合并。

**最终回复要求：** 已验证的连续区间及其截断上限、各个 PR 的独立裁决结论及给出裁决的 Agent 详情、已开启的合并机制及确认依据、已正式落地的 PR 清单，以及打通后续质量断层所需的具体前置条件。
