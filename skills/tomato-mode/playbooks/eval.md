### 评测（Eval）

**对评测实验设计负全责。严密规划、双盲隔离、并发执行、综合裁决。**

评测（Eval）旨在正式推广某项改动前，量化测定其对 Agent 行为模式的实际影响（例如评估新的技能变体、系统结构调整或 Prompt 微调效果）。该流程的核心风险是“观察者效应（Observer effect）”：意识到自身处于评测环境的 Agent 会产生行为偏差，因此所有候选 Agent 必须在严格的盲态（Blind）下运行。

**双盲隔离的硬性约束：**

- 候选 Agent 可见的任何目录、文件名或 Prompt 文本中，严禁出现 `eval`、`test`、`judge`、`experiment`、`rubric`、`score`、`compare`、`benchmark`、`candidate` 或 `arena` 等暴露评测意图的特征词。
- 发给候选 Agent 的 Prompt 必须完全模拟真实自然的用户业务诉求。只描述具体任务目标，严禁泄露元指令信息。例如应写“帮我实现一个轻量的 Todo CLI 工具”，而非“请演示你如何严格遵循各项工程原则”。
- 严禁给出任何诱导性线索。不要要求候选 Agent 自行罗列其调用了哪些技能、原则或规则文件（此类元提问会人为放大规则引用行为）。仅需通用地要求其提供设计说明，随后从生成代码的真实结构与形态来客观评判其是否遵循原则，绝不依据其自述文本。
- 清洗测试工作区目录名与项目标识（slug）。使用符合真实业务场景的项目名称，严禁使用 `candidate-1` 或 `agent-a` 等评测标签。
- 严禁向候选 Agent 透露存在其他并发候选方案。
- 裁判模型可以知晓自身处于评审角色，但仅能看到经匿名化清洗的方案代号与产物，绝对不可见真实的 Agent 类型或模型标识。
- 在对比两个方案变体时，必须由同一位裁判在单次推理过程中使用统一的评分标准同时对两组产物打分，且裁判不得知晓各产物对应的具体变体。使用不同 Prompt 分两次调用裁判模型会导致评分基准漂移，失去可比性。

**执行步骤：**

1. **明确评测目标。** 阐明受测的方案变体以及判定成功的行为特征。为裁判编写结构化评分细则（包含 3 到 6 条明确具体的打分维度），该标准对候选 Agent 严格保密。
2. **搭建匿名隔离环境。** 为每个候选方案创建独立的测试目录并预置对应变体。注入真实自然任务应有的全部上下文：包括工程脚手架以及正常业务流程中自然需要读取的技能文件。
3. **编写拟真 Prompt。** 模拟真实用户的自然表达，不泄露任何评测意图与度量指标。
4. **并行派生 N 个候选 Agent。** 按照 **arena** 技能 Phase B 规范分配 Agent 类型。各 Agent 在各自独立的匿名环境中基于完全相同的 Prompt 并行执行。
5. **派生盲态裁判 Agent。** 按照 **arena** 技能 Phase C 规范选取来自不同供应商的独立模型担任裁判。裁判仅接收匿名化代号与评分标准，严禁接触底层 Agent 类型。
6. **基于会话记录核查实际执行链，严禁轻信自述。** 在当前工作区的 `<slug>` 目录下，读取每个候选者的本地会话记录 `~/.claude/projects/<slug>/<uuid>.jsonl`（严禁使用 `~/.claude/projects/*/` 进行全局通配，以免越界读取其他项目的历史会话；当前工作区 `/Users/xiongzhipeng/.agents` 对应目录为 `~/.claude/projects/-Users-xiongzhipeng--agents/`）。核查候选 Agent 实际打开读取了哪些文件。在文本中提及某项原则并不等同于真正阅读了其原则细则文件，阅读了也不等同于在代码中真正贯彻。是否遵循原则链，必须由其真实读取的文件记录结合最终代码结构进行客观检验，绝不采信候选者的单方自述。
7. **亲自通读所有候选产物。** 对照裁判给出的评审结论进行交叉比对。若出现分歧，往往意味着特定模型存在固有偏见或评分标准存在歧义。由你给出最终的综合裁决。

**最终回复要求：** 受测变体说明、评分细则标准、各候选方案详细评估、裁判裁决记录、你的最终综合裁定，以及关于是否正式推广该变体的明确建议。
