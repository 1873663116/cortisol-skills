### 调查（Investigation）

**对调查结论的准确性负全责。严密规划、精准路由、高质量撰写。**

适用于只读性质的技术咨询：“X 是如何运作的？”“Y 当初为何如此设计？”“Z 这件事结论是否可靠？”“究竟该做 X 还是做 Y？”。该流程的交付物为附带确凿出处的原理解释或架构建议，而非代码改动。

1. **精准路由。** 路由至 **how** 技能（具体实现细节使用“讲解模式”，涉及“我们确定要这么做吗”的存疑点使用“批评模式”）。涉及设计动机与技术选型背景的问题同时路由至 **why** 技能。
2. **记录简化检查点。** 吞吐检查点单行记录为 `throughput checkpoint: n/a, read-only investigation`。四项完整版检查点仅适用于代码改动类任务。
3. **输出结构化分析。** 产出符合 `how` 规范的结构化内容（架构概览 / 核心概念 / 运行时机理 / 关键代码定位 / 常见陷阱与注意事项）。若咨询旨在多个方案间做抉择，输出明确的技术建议并附带详尽的利弊权衡对比表。
4. **去 AI 腔清洗。** 对最终回复严格应用 **unslop** 技能进行去 AI 腔审查。

不新建 PR，不执行 Babysit，亦不调用 `architect`（除非本次调查明确属于后续代码改动的前置环节；若确属前置调研，将调查结论交付用户后，重新路由至 Bug fix 或 Feature 流程）。

**最终回复要求：** 调查分析结论。针对“我们确定要这么做吗？”类问题，必须给出你的真实技术判断与明确理由。若用户问题的前提假设本身存在缺陷，必须直接指出并予以纠正（遵循 Autonomy 章节准则）。
