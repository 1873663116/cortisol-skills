### 爬山优化（Hillclimb）

**对优化指标与实验严密性负全责。做好统筹监督与代码审查，将具体优化尝试委派出去。** 适用于针对特定目标，对可量化指标进行持续、科学迭代优化的场景（如“针对 X 进行爬山优化”“将冷启动时间缩短 50%”“系统性压降某项指标”“持续迭代直到指标改善 N% 为止”）。单次修复属于缺陷修复（Bug fix）或性能问题（Perf issue），本流程专指循环迭代优化。

核心纪律：每次仅允许引入单项改动，执行单次测量，根据数据明确决定保留或回滚。严禁将多项未经单独测试的改动混在一起提交，严禁仅凭代码走读就主观断定取得成效。一切以实测数据为唯一准绳（遵循**用实际运行证明有效**原则）。

1. **摸清负载并锁定度量标尺。** 在确立度量标尺前，必须先透彻理解工作负载特征与系统架构。针对目标模块调用 **how** 技能，明确识别对运行结果产生实质影响的负载维度（数据规模、历史记录深度、内部状态复杂度、并发度），并选取能够稳定复现性能瓶颈的典型用例。若无现有用例能复现瓶颈，必须先构造复现用例，严禁在无法复现基线的情况下盲目优化。随后锁定核心指标、优化方向（越大越好还是越小越好），以及可程序化判定的终止条件。该终止条件必须将目标阈值与最低迭代轮次绑定，防止偶发性的早期幸运波动导致优化过早终止（例如“指标较基线提升至少 50% 且至少执行 10 轮有效迭代”）。用户给出具体数字时遵循用户要求，否则与用户明确商定。
2. **构建并严格冻结测量工具。** 构建测量工具脚本，验证其具备足够的度量分辨力，随后将其严格冻结（遵循**打造杠杆工具**原则）。运行多组形成鲜明对照的真实负载，验证目标用例能稳定触发症状，而轻量用例能够被有效区分。若度量标尺无法体现差异，必须重新调整测试负载或指标口径。测试工具一旦冻结，必须通过单一可重复命令输出指标数值，采样次数必须足以抹平环境噪声（例如取 N 次测量的中位数，严禁只测单次）。测试工具的任何改动都将导致此前采集的数据全部失效。在动手改动代码前，先记录基线指标数据，并确保回归测试门禁（所有必须持续通过的既有用例）全部绿态通过。
3. **初始化决策日志。** 通过 **show-me-your-work** 技能初始化决策日志文件（`decision.tsv`）。每次尝试占一行，记录：尝试序号、假设描述、改动内容、改动前数值、改动后数值、差值变化、测试结果、裁决结论（保留/回滚）、补充备注。这是整个迭代过程的共享持久记忆。每次提出新尝试前必须先查阅该日志，确保优化探索持续累积而非原地打转。将该文件置于版本控制之外（配置到 `.gitignore`），确保其在执行代码回滚操作时不被冲掉。
4. **提出扎根架构的具体假设。** 每个优化假设都必须扎根于步骤 1 建立的系统架构模型，明确指出具体的瓶颈机理（例如“将 X 移出主启动链路，因为它直接阻塞了首帧渲染”），严禁提出“随手加个 memo 试试”等盲目假设。
5. **循环迭代验证单项假设：**
   - 阅读 **dispatch** 技能规范选定 `Letter-precise` 角色，经 **orchestration** 技能派发具体改动，严格收紧改动范围。自身专注于监督与审查，严禁亲自逐行敲代码（遵循**守卫上下文窗口**原则）。当存在多个互不相交的独立假设时，可并行派发多个 Worker，各自在独立的 worktree 中执行以防代码冲突（遵循**在串行化共享状态前先消除共享**原则）。
   - 使用已冻结的测试工具测量改动前后的真实指标，并完整运行回归测试门禁。
   - 仅当指标改善幅度明确超出噪声波动范围且回归门禁保持全绿时，方可接受该改动。否则必须坚决完整回滚该改动，严禁让“说不定有用”的微小改动搭便车混入。
   - 每接受一项有效改动即单独提交一次 commit，仅暂存该改动涉及的具体文件（`git add <files>`，严禁使用 `git add -A`）。无论最终保留还是回滚，均须在决策日志中记录对应行。
   每轮迭代均须以一次严格检查收尾，随后方可开启下一轮（遵循**将工作划分为闭环可验证单元**原则）。若本轮为无人值守的自动化运行，仅从自主运行 playbook（`playbooks/autonomous-run.md`）借用其唤醒机制，严禁套用其终止规则。终止判定严格以本 playbook 下方的停止条件为准；遇到性能平台期意味着需要转换优化策略，而非直接终止流程。
6. **全力攻克首个平台期。** 当优化陷入停滞或连续多次尝试被否决时，应主动切换策略方向、尝试组合若干接近成功的思路、重新精读源码，或探索更具颠覆性的重构方案，随后方可得出已达优化极限的结论。代码正确性与结构精简度的优先级始终高于纯粹的指标数字。破坏既有正确行为的“优化”必须回滚，而在保住指标前提下所做的代码精简则应坚决保留（遵循**极简工程原则**）。
7. **满足条件后终止。** 当终止判定条件满足，或剩余待验证思路的边际收益确实极低、已无法支撑其改动成本时，方可停止流程。严禁通过人为放宽终止条件来虚假宣布胜利，在尚有低成本且未经验证的假设时严禁半途而废。若陷入技术卡点，必须如实阐明，严禁无意义空转。
8. **执行开 PR（Opening a PR）。** 将所有被接受的 commit 按照落地时间顺序依次堆叠，使指标的攀升轨迹在 Git 历史中清晰可辨。

**最终回复要求：** 核心指标与目标阈值、从基线到最终值的绝对值与百分比变化、总迭代轮次（接受数与回滚数对比）、逐行罗列各项被接受的优化点、`decision.tsv` 的存放路径，以及若继续推进后续最优先推荐尝试的方向。
