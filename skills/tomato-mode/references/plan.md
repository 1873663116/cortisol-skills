# 实施计划编写规范（Plan）

产出一份分阶段的严密实施计划，其技术底座为 `tomato-mode` 的 **Principles** 章节。计划文档本身即是当前交付物，在获得用户确认前严禁直接动手编码实现。

建立一个待办清单（todolist），下方各步骤一一对应一项。

## 0. 前置评估与分流

改动仅涉及 1 到 2 个文件且实现方案显而易见时，跳过编写正式计划文档。向用户明确说明这一点并结束流程。

改动涉及 3 个及以上文件、引入新的系统架构、存在多个相互竞争的技术方案、业务范围边界模糊，或用户显式要求提供实施计划时，必须撰写正式计划。

## 1. 深入研读核心工程原则

完整通读 `tomato-mode` 技能的 **Principles** 章节及其索引的所有 `principle-*` 细则文件。工程原则贯穿并支配计划中的每一项架构决策，在计划中必须显式进行交叉引用。

## 2. 明确范围与系统约束

用一段精炼文本阐明你对任务范围与边界约束的理解。仅在需求意图确实模糊不清时，方可调用 `AskUserQuestion`（遵循**可逆操作严禁阻塞等待人类**原则）；提出的每个未决问题均须附带具体的备选选项。

清晰界定：哪些属于明确范围、哪些明确排除在外、技术栈或运行平台约束、必须保留的既有设计模式，以及严格的验收完成定义（Definition of Done）。

## 3. 委派子 Agent 探索代码库

将代码库检索与探索任务经 **orchestration** 技能委派（遵循**守卫上下文窗口**原则）。

- 阅读 **dispatch** 技能规范，选取其 `Bulk`（大体量）类别。
- 将完整的探索 Prompt 派发给探索 Worker。在任务指令中明确注明 `Do not write or modify files`（只读探索，严禁修改文件）。

探索子 Agent 须返回具体文件路径索引、架构约定、依赖关系、测试基础设施以及核心入口点。严禁在主线程内联倾倒大段原始代码。

## 4. 撰写分阶段实施计划

计划文档的存放位置由用户指定。

小型轻量计划统一采用单个文件 `NN-slug.md`。包含 3 个及以上阶段的复杂计划，必须组织为独立目录结构，包含 `overview.md` 与各个独立的阶段分册：

```
NN-slug/
├── overview.md
├── phase-1-scaffold.md
├── phase-2-...md
└── testing.md
```

### 阶段切分粒度标准

- 单个阶段规模：单个函数或单个核心类型及其配套测试，或单一明确的 Bug 修复。严禁粗暴以“单个文件”为阶段单位。
- 单个阶段最多涉及 2 到 3 个文件。
- 宁可切分为 8 到 10 个小巧紧凑的阶段，也绝不合并为 3 到 4 个庞大臃肿的阶段，以保持充足的架构调整回旋空间（遵循**底层先导思维**原则）。
- 单个阶段包含超过 5 个测试用例或 3 个核心函数时，必须进一步拆分。

### Overview 总览文件结构

- **背景。** 核心解决什么问题，为什么当下必须实施。
- **范围。** 包含哪些改动；明确排除哪些内容。
- **约束。** 技术栈、平台依赖、第三方依赖、既有架构模式。
- **方案比选。** 勾勒 2 到 3 个相互竞争的技术方案，给出最终选型结论及充分的技术理由（遵循**穷尽设计空间**原则）。若受客观约束限制仅存在唯一定解时可跳过比选。
- **适用技能。** 实现阶段应当调用的具体技能清单，必须明确点名。
- **阶段划分。** 按执行顺序以标准 Markdown 链接指向各个阶段分册文件。
- **全量验证。** 项目级别的端到端验证命令。
- **实施指引。** 参见下文第 6 节。

### 阶段分册文件结构

- 顶部必须包含指向 `overview.md` 的反向链接。
- **目标。** 本阶段的核心交付成果。
- **改动清单。** 涉及的具体文件路径，以及改动的概要说明。重点描述“做什么”与“为什么”，不写具体实现伪代码，不贴大段代码块。
- **数据结构与形态。** 明确核心类型定义或 Schema 结构。仅需单行抽象草图（遵循**底层先导思维**原则）。
- **阶段验证方案。** 参见下文第 5 节。

合理安排执行顺序，确保基础设施脚手架与共享核心类型优先落地（遵循**底层先导思维**原则）。每个阶段在逻辑上都应具备独立验证与上线的完备性。

针对触碰既有代码的改动，严格贯彻**第一性原理重构**原则：设想若从第一天起就带着这项新需求构建系统，它应呈现何种优雅形态？通盘重新设计，增量交付落地。

若某一阶段涉及创建或修改技能定义，必须在计划中明确指示实现者调用 **writing-for-agents** 技能并研读其技能机制章节。

## 5. 各阶段的独立验证方案

每个阶段均须包含双重闭环验证：

**静态验证。** 严格通过类型检查（Typecheck）、代码规范检查（Lint）以及项目既有单元测试套件。

**运行时动态验证。** 利用可用的自动化工具，在匹配的宿主环境下对功能进行端到端实测运行：

- 浏览器、Electron 及 Web UI：调用 **playwright** 技能。
- CLI 与 TUI：本地无专用驱动技能，在计划中明确安排手动操作步骤。
- 移动端原生应用：使用团队现有的模拟器驱动技能。
- 无可用自动化驱动工具的特殊界面：在计划中明确如实标出。

对于 Bug 修复任务，验证闭环固定为：在宿主界面稳定复现、实施修复、在相同界面上验证通过。单元测试仅能覆盖局部特定分支，无法证明 Bug 在全局真实环境下已被彻底消除（遵循**用实际运行证明有效**原则）。

## 6. 实施指引规范

在 `overview.md` 中必须明确列出实现者必须严格遵循的 `tomato-mode` 核心硬性准则：

- 改动任何不熟悉的子系统前，必须先调用 **how** 技能透彻理解其实现脉络。
- 存在争议的架构设计在合并上线前，必须调用 **interrogate** 技能执行对抗式深度审查。
- 提交每个 commit 前，以及输出任何自然语言文本时，必须严格应用 **unslop** 技能进行去 AI 腔清洗。
- 计划规模宏大、需要可审计记录时，调用 **show-me-your-work** 技能记录完整的决策记录链。
- 提交 PR 后，启动 Cursor 内置的 **babysit** 技能进行持续看护。

## 7. 交付并交回控制权

汇总输出各阶段摘要、边界范围、适用技能清单及验证手段。立即停步，将何时开启具体实现的决定权完整交还给用户。
