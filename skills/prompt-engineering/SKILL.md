## Runtime context

LLM 运行时上下文，是任务中实际提供给 LLM 的全部信息。其来源包括 System Instructions、Developer Instructions、Tool Definitions、Skill Descriptions、已加载的 SKILL.md、User prompt等执行过程中补充的其它信息。它们具有不同的权威层级、适用范围和可见性。

同一运行环境中的 Agent 通常共享大部分运行时上下文。

因此，每项规则或事实应有明确的权威来源，并放在能够以正确覆盖其使用者的最低层级。设计下游 LLMs 上下文时，应只补充其完成职责所必需的新增内容、约束和例外等，不重复已有信息。
如果接收者无法可靠获得必要的上游内容，则应携带缺失信息，并明确其来源与适用范围。

目标不是机械地消除重复，而是在保证职责所需信息充分的前提下，避免同一语义由多个位置独立定义。
语义重复无法仅靠格式或静态规则可靠识别。新增或修改 LLM 运行时文本后，应针对接收者实际获得的完整上下文链检查，不只是当前文件。


## Agent prompt

派遣其他 Agent 时，应将其视为另一个拥有相同基础和判断能力的自己：不需要描述其描述其已能获得的信息，不需要指导其已能自主完成的行为，只提供任务目标、未知信息和必要约束；prompt 应模拟人类专家之间的任务委托，而不是操作手册。


## Artifact management

对于 LLM 维护或生成的 Artifact：
- 当系统状态发生变化时，Artifact 的内容更新（比如术语、架构，路线等）仅包含最新表达，不累积、不体现任何决策过程、指令或变化痕迹。
- 最终内容应作为系统当前权威状态的直接表达和单一事实来源，就好像历史残留、被否定的内容等完全不存在，而只描述系统“现在是什么”，使后续 Agent 能基于当前有效状态进行理解和推理；
	反例：这不是X，而是Y
	正确：这是Y
- 决策记录、log 等内容可以豁免该规则。


## 设计 LLMs 工具

机械可重复的步骤，适合由程序、脚本或工具执行； 
需要结合上下文和目标进行权衡损益的决策，适合由 LLM 执行。

因此，在设计 LLM 运行时工具时（如 skill ）：
- 脚本和工具负责获取事实、执行确定步骤和验证机械条件；
- LLM 负责处理例外并作出情境化决策。 

预算、数量、上限和阈值等通常就被视为需要结合任务权衡的决策信号。只有存在明确要求时，才设为硬限制。
