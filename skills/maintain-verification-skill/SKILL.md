# Maintain Verification Skill

一旦应用程序发生代码迭代，原有的功能地图与验证规程极易发生时效性腐化。本技能是针对由 `/create-verification-skill` 生成的验证技能（或任何包含功能地图的项目级验证技能）的周期性维护闭环。核验的基本单元是具体的**功能（Feature）**，而非孤立的字面语句：基于源码实现完整覆盖每个功能分册，并通过真实运行对每个功能进行动态实测验证。

## 最终判定结论

最终产出必须明确归为以下三类之一：

- **clean**：所有功能均通过了源码审查与真实动态实测验证，未发现需要修正之处。不创建分支，不开启 PR。
- **changed**：产出且仅产出一个 PR，包含经过严格实测证明的文档修正、测试工装修复或功能地图更新。
- **blocked**：验证覆盖未能顺利完成，或确凿的修复无法安全合入。必须精准指明具体的阻塞根因。

## 编辑边界限制

**严禁在执行本技能期间修改业务产品代码**：修改范围严格限定在验证技能自身的目录内部（其 `SKILL.md`、`features/` 目录以及其拥有的工装测试脚本）。若功能地图所描述的业务行为与应用程序实际表现不一致，只有两种可能：要么是文档发生漂移（修改功能地图以匹配实际行为），要么是产品发生功能回归（将其作为独立缺陷如实向用户上报，严禁在文档中通过篡改规格进行掩盖）。

## 执行规程

0. **定位目标技能**：在仓库中检索待维护的项目级验证技能（通常位于 `.claude/skills/verify-*/` 目录下，包含启动/驱动章节与功能地图）。若存在多个候选，向用户求证；若不存在，停步并引导使用 `/create-verification-skill`。
1. **清理功能索引**：通读功能地图 README 并检索同级分册文件，快速修复缺失、多余、重复或失效的死链接条目。
2. **源码并发审查**：查阅 **dispatch** 技能规范，选用其 `Bulk` 类别。为每个功能分册各派发一个独立审查 Worker，并发执行。任务中显式注明 `Do not drive the app or write or modify files`。各个 Worker 基于最新源码剖析“该面向用户的功能是如何实现的”、对照功能地图标出疑似文档漂移并附带代码引用，并提炼出一份精炼的真实环境实测配方。
3. **综合与去重**：聚合各 Agent 返回的分析结果，将重叠的实测配方合并为尽可能少的系统运行状态。抽检有争议的漂移点，结合近期的 Git 提交历史排查是否存在遗漏的新功能分册。
4. **真实环境动态实测**：即使源码走读看起来完全正常，**真实动态实测亦是必不可少的硬性要求**。由主协调者统一掌管应用的启动与驱动执行，严格遵循验证技能自身的启动模型（对服务与 UI 采用长生命周期实例进行串行驱动，对轻量 CLI 采用独立会话驱动）。全面遍历实测每个功能至少一次，全流程坚决守护三大不变量：
   - **绝不驱动未经验活的异常实例**：在首次驱动前执行健康检查（Doctor）；若实例发生非预期异常，必须先执行诊断检查，无法恢复时彻底重启重置，严禁抱侥幸心理继续运行。
   - **已捕获的测试证据在任何清理操作中必须安全留存**。
   - **单次驱动启动的临时资源绝不能残留外溢**：无论测试成功与否，彻底清理临时残留数据。
   若应用中某功能确实无法触达（如受限于特定权限、外部系统依赖或硬件环境），必须明确记录其具体前置依赖与尝试路径，定性为 `verified-unreachable`。对测试工装脚本的任何修改，在正式合入前必须通过真实运行予以二次验证。
5. **缺陷分流分类**：
   - 用户视角的描述错误或遗漏 → 定性为文档漂移，就地修正。
   - 应用程序功能正常但自动化工装无法正确驱动 → 定性为工装缺陷，就地修复工装脚本。
   - 应用程序自身存在实质性功能 Bug → 定性为产品缺陷，如实向用户记录汇报，严禁纳入本次 PR 中。
6. **合入或终止**：若为 `changed` 状态，提交一个包含所有证明有效的修正的 PR（在提交前重新完整通读所有修改的文件）；若为 `clean` 或 `blocked` 状态，不开启 PR，如实向用户汇报覆盖度与阻塞详情。
